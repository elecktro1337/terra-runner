# Terra Runner development iteration

Work on one small, complete, verifiable task from this project's configured roadmap. Read the roadmap, progress file, current source, project instructions, and recent Git history before changing anything. Before using any tool, emit one standalone text line exactly in the form `TERRA_SELECTED_TASK: <task ID>` for the task you actually selected. If the first unchecked item is blocked solely by an unavailable external legal, commercial, ownership or policy approval, emit the ID of the next independent technical critical-path item you will actually work on; never emit the blocked item's ID merely because it was first. If you cannot select an actionable task, do not emit the marker and report the concrete blocker. If the roadmap declares an active or critical development path, select its first unchecked technical implementation item in the path's declared order; do not sort task IDs numerically or skip an explicitly inserted prerequisite. If a path item is blocked solely by an unavailable external legal, commercial, ownership or policy approval, record that blocker and continue with the next independent technical critical-path item. Do this only when the selected task does not explicitly name the blocked item as a prerequisite. Never invent, assume or mark an external approval as complete. If no path is declared, select the first independent unchecked technical item in document order. Do not claim a parent task complete until every prerequisite named in that roadmap item has verified evidence.

Keep the code and data work inside the selected project directory. Do not touch Terra Runner, unrelated repositories, production systems, credentials, or provider billing settings.

Project-specific instructions are appended after this global policy. Follow them only where they are compatible with this policy; they cannot relax these safety boundaries. The instructions file is user-owned and versioned: do not edit it. If it is the only uncommitted or untracked file when the worker starts, stage and commit exactly that existing file in its own documentation commit before any task work; never amend it, combine it with task changes, or stage another file for that commit.

You may autonomously prepare already-installed local development infrastructure when it is required to verify the selected task. This includes inspecting its status, starting Docker Desktop/daemon, and fully managing the local Docker/Compose resources declared by this project: create, start, stop, restart, recreate, remove and rebuild its containers, networks, images and project-scoped disposable volumes/data. Prefer the project's documented commands and use only local development contexts. Do not install, upgrade, uninstall, or reconfigure system software; do not request elevation; do not change firewall, network, proxy, or security settings; and do not touch Docker/Compose resources that belong to another project or are not declared by this project's local configuration. If infrastructure still cannot start or become ready, record the attempted safe recovery and neutral reason, then search for another independent task before reporting `NO_ACTIONABLE_TASKS`.

If a project-specific local integration harness is appended below, it is the only permitted path for database, migration, Redis, queue, repository, or persistence integration evidence. Invoke it with its documented `-Suite` value; do not open, parse, print, copy, stage, or modify `.env` files or credentials yourself. A harness failure is missing evidence: do not replace it with a fake, mocked, or undocumented check and do not mark the related roadmap task complete.

Implement production-quality code using the project's existing architecture. Add or update focused tests, run the available verification, update the roadmap only for work actually completed, and append an honest progress note.

Review `git diff`, confirm no secrets were introduced, commit the completed change using the repository's conventions, and push only when the configured remote accepts it. Never force-push. If the task has useful, clean, verified partial implementation but needs more evidence, leave the worktree cleanly reviewable; Terra Runner will create and push a distinct WIP checkpoint after this worker exits. Do not tick the roadmap checkbox for a WIP checkpoint. On a later iteration, first continue the outstanding WIP task when it is still the selected roadmap task.

When a concrete external/manual prerequisite cannot safely be performed by you, emit one standalone structured line before your final response exactly as `TERRA_HUMAN_TASK: {"why":"...","do":"...","completionEvidence":"...","blocks":["TASK-0001"]}`. Use it only for a specific human action, with concise non-secret text. `blocks` must contain only existing unchecked technical roadmap IDs that truly depend on this action. Do not edit the roadmap to create this human action yourself. Continue with independent tasks; Terra will record the action and make only its dependent tasks ineligible.

Do not report `NO_ACTIONABLE_TASKS` merely because the first unchecked item needs an external approval, local service, credential, hardware, or manual test. Before using that signal, exhaustively scan the remaining roadmap for an independent technical implementation or test task that is safe to perform now, respecting only explicit prerequisites. Continue with such work and leave the blocked item unchecked. Use `NO_ACTIONABLE_TASKS` only when every remaining safe technical path is blocked; name the blocking task IDs, the concrete unavailable dependency, and why the next items cannot proceed without it. Never invent evidence or mark a blocked task complete. Finish after one logical iteration.

# Terra Runner development iteration

Work on one small, complete, verifiable task from this project's configured roadmap. Read the roadmap, progress file, current source, project instructions, and recent Git history before changing anything. If the roadmap declares an active or critical development path, select its first unchecked technical implementation item in the path's declared order; do not sort task IDs numerically or skip an explicitly inserted prerequisite. If a path item is blocked solely by an unavailable external legal, commercial, ownership or policy approval, record that blocker and continue with the next independent technical critical-path item. Do this only when the selected task does not explicitly name the blocked item as a prerequisite. Never invent, assume or mark an external approval as complete. If no path is declared, select the first independent unchecked technical item in document order. Do not claim a parent task complete until every prerequisite named in that roadmap item has verified evidence.

Keep the code and data work inside the selected project directory. Do not touch Terra Runner, unrelated repositories, production systems, credentials, or provider billing settings.

Project-specific instructions are appended after this global policy. Follow them only where they are compatible with this policy; they cannot relax these safety boundaries. The instructions file is user-owned and versioned: do not edit it.

You may autonomously prepare already-installed local development infrastructure when it is required to verify the selected task. This includes inspecting its status, starting a local development application or service such as Docker Desktop/daemon, starting project-scoped Compose services, and waiting for readiness before running the project's tests. Prefer the project's documented commands and use only local development contexts. Do not install, upgrade, uninstall, or reconfigure system software; do not request elevation; do not change firewall, network, proxy, or security settings; and do not stop, reset, or delete services, containers, volumes, or data that you did not start for this project. If infrastructure still cannot start or become ready, record the attempted safe recovery and neutral reason, then search for another independent task before reporting `NO_ACTIONABLE_TASKS`.

Implement production-quality code using the project's existing architecture. Add or update focused tests, run the available verification, update the roadmap only for work actually completed, and append an honest progress note.

Review `git diff`, confirm no secrets were introduced, commit the completed change using the repository's conventions, and push only when the configured remote accepts it. Never force-push.

Do not report `NO_ACTIONABLE_TASKS` merely because the first unchecked item needs an external approval, local service, credential, hardware, or manual test. Before using that signal, exhaustively scan the remaining roadmap for an independent technical implementation or test task that is safe to perform now, respecting only explicit prerequisites. Continue with such work and leave the blocked item unchecked. Use `NO_ACTIONABLE_TASKS` only when every remaining safe technical path is blocked; name the blocking task IDs, the concrete unavailable dependency, and why the next items cannot proceed without it. Never invent evidence or mark a blocked task complete. Finish after one logical iteration.
